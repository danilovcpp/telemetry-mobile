# Часть A. Контекст и обязательные уточнения

## A.0. Окружение — проверь первым делом

1. `dotnet --list-sdks` — нужен SDK 10.0.4xx (проект на `net10.0-*`).
2. `dotnet workload list` — должны быть установлены MAUI workloads (как минимум `maui-android`, на Windows также `maui-windows`). На предыдущем ПК их не было, и сборка падала с `NETSDK1147`. **Если workloads нет — остановись и сообщи пользователю.** Не устанавливай их сам без подтверждения: это MSI-установка с правами администратора.
3. Для Android-сборки нужны Android SDK и JDK (обычно ставятся вместе с Visual Studio). iOS/MacCatalyst собираются только на macOS — на Windows их не собирай и в отчёте так и укажи.
4. Всегда собирай с явным `-f`: без него восстанавливаются все target-фреймворки, и сборка падает, если хоть одного workload нет.

   ```powershell
   dotnet build TelemetryMobile/TelemetryMobile.csproj -f net10.0-android
   dotnet build TelemetryMobile/TelemetryMobile.csproj -f net10.0-windows10.0.19041.0
   ```

Проверено анализом кода (см. также `CLAUDE.md` в корне):

## A.3. Спецификация API доступна — это меняет раздел 10 ТЗ

В части B сказано «спецификация будет предоставлена отдельно, до неё не реализуй сетевые вызовы». **Спецификация предоставлена.** Поэтому:

1. **Интерфейс источника данных проектируй сразу под контракт API**, а не под пример из раздела 9 части B:
   - `GetDevicesAsync(int customerId, CancellationToken)` → список устройств (сортировка по `name`, затем `id`);
   - `GetDeviceAsync(int deviceId, CancellationToken)` → карточка устройства;
   - `GetDeviceEventsAsync(int deviceId, int limit, string? cursor, CancellationToken)` → страница `{ Items, NextCursor, HasMore }` (курсорная пагинация, новые сверху: `occurredAtUtc` desc, затем `id` desc).

   Интерфейс возвращает модели приложения, а не DTO; DTO API (`DeviceListItemDto`, `DeviceDetailsDto`, `DeviceEventDto`, `PagedResultOfDeviceEventDto`, `ProblemDetails`) живут только внутри HTTP-реализации и маппятся в модели приложения.

2. **Реализуй обе реализации:**
   - `MockDeviceTelemetryService` — источник по умолчанию. Ведёт себя как API: та же сортировка, та же курсорная пагинация с непрозрачным курсором, те же ошибки (см. A.5).
   - `ApiDeviceTelemetryService` — реальный HTTP-клиент по спецификации. `HttpClient` создаётся через DI (typed client / `IHttpClientFactory`), не в страницах и не во ViewModel. Никаких вызовов при логине.
   - Выбор источника — в Settings, секция «Источник данных»: «Демо» (по умолчанию) или «Сервер» с полем базового URL. Значения хранятся в `Preferences`. Смена источника сбрасывает загруженные данные и возвращает на список устройств. Базовый URL staging неизвестен — не выдумывай его; без URL режим «Сервер» недоступен.
   - Staging работает по HTTP. Для Android добавь **только для Debug** `network_security_config.xml`, разрешающий cleartext для `10.0.2.2` и `localhost` (эмулятор), и опиши в отчёте, куда вписать хост staging. Для iOS не добавляй ATS-исключения вслепую — опиши шаг в отчёте.

3. **Логин по-прежнему без HTTP** (раздел 4 части B в силе). `customerId` в API — `int32`, поэтому валидация Customer ID: обязательное поле, целое число от 1 до 2147483647, числовая клавиатура.

## A.4. Статусы устройств и health-check — расхождение ТЗ и API

API 1.0.0 **не содержит** состояния Online/Warning/Offline, heartbeat и health-check и прямо запрещает выводить «онлайн/офлайн» из давности события (`docs/mobile-api.md`, раздел 6). Решение:

- В модели приложения есть `DeviceHealthState { Unknown, Online, Warning, Offline }` и необязательные поля `LastHealthCheckAtUtc`, `LastEventAtUtc`, `LastStatusCode`.
- **Mock** заполняет их явно заданными демо-значениями (по набору из раздела 11 части B). В демо-режиме показывай ненавязчивую отметку «Демо-данные» (на Devices и в Details), чтобы демо-статусы не выдавались за реальные.
- **API-реализация** всегда отдаёт `Unknown` и `LastHealthCheckAtUtc = null`. Не вычисляй статус из `statusCode` или из времени события.
- `lastStatusCode`/`lastEventAtUtc` подписывай как **последний известный статус с датой** («Последний статус 200 · 16 окт, 12:05»), а не как текущее состояние.
- **Список устройств в API содержит только `id`, `deviceCode`, `name`.** Не запрашивай карточку каждого устройства при открытии списка (лимит 120 запросов/мин на IP, раздел 4 спецификации). Поэтому карточка в списке должна корректно выглядеть и без времени события/кода статуса: показывай локализованное «Нет данных» / `Unknown`, а не пустые строки.
- Сводка в шапке Devices («в норме» / «требуют внимания») считается только по известным состояниям; если все `Unknown` — показывай «Статус недоступен», а не нули, выдающие себя за данные.
- «Количество событий» в Details: в API его нет → `Not available`. Не листай всю историю ради подсчёта.

## A.5. Ошибки, лимиты, пагинация — по спецификации

- Ошибки API — RFC 9457 Problem Details; логику строй на HTTP-статусе и `code`, **`detail` пользователю не показывай**. Ошибки валидации 400 приходят без `code`, с `errors`.
- Введи типизированную ошибку источника данных (например, исключение с `Kind`: `CustomerNotFound`, `DeviceNotFound`, `InvalidCursor`, `RateLimited` + `RetryAfter`, `Unavailable` + `RetryAfter`, `Network`, `Unexpected`; плюс `TraceId`, если есть). ViewModel превращает её в локализованное сообщение. `traceId` можно показать мелким текстом в деталях ошибки.
- Поведение клиента (таблица в разделе 3 спецификации):
  - `customer.not_found` → состояние «Клиент не найден» на экране Devices с действием «Выйти»;
  - `device.not_found` → закрыть экран устройства/событий, вернуться к списку и обновить его;
  - `pagination.invalid_cursor` → сбросить историю и загрузить первую страницу;
  - 429 и 503 → сообщение «повторите через N с» по `Retry-After`; никаких автоматических фоновых опросов.
- Mock воспроизводит: customer **1** — 6–8 устройств; customer **2** — существует, устройств нет (пустой список); любой другой — `CustomerNotFound`. Это и есть «явно документированный сценарий» из раздела 11 части B. На Staging у клиентов 1–10 по 5 устройств — это не противоречит mock, т. к. mock не притворяется сервером.
- История событий: размер страницы 20, бесконечная прокрутка (`RemainingItemsThreshold`), pull-to-refresh **заменяет** список целиком (не дописывает), ключ элемента — `id` события (UUID). Recent events в Details — первая страница с `limit = 5`. `limit` всегда в диапазоне 1–100.

## A.6. События: тип, описание, payload, время

- Справочника кодов в API нет. Единственные документированные коды: `100001` — ошибка устройства, `100002` — низкий заряд (раздел 9 спецификации). Введи один централизованный каталог кодов (`IStatusCodeCatalog` → тип события + ключ локализованного описания):
  - базовый каталог знает только `100001` (Error) и `100002` (Warning);
  - всё остальное — нейтральный тип и описание «Обновление статуса» с показом кода как есть;
  - чтобы в демо были события «нормальный health-check», «предупреждение», «ошибка», «восстановление», mock использует **отдельные демо-коды**, известные только демо-каталогу (регистрируется вместе с mock). Демо-коды не должны пересекаться с реальными (`200`, `100001`, `100002`).
- `payload` — произвольный JSON-объект до 8 КБ или `null`. Храни как `JsonElement?`/словарь; в карточке списка не выводи JSON; в подробностях события (отдельный экран или раскрывающаяся панель) показывай пары ключ–значение верхнего уровня, вложенные значения — компактным JSON. Разбор защищённый: отсутствующие ключи и неожиданные типы не должны ронять экран.
- Время: `DateTimeOffset` из UTC; показывай `occurredAtUtc` в локальном поясе. `System.Text.Json` принимает дробную часть от 0 до 7 знаков — покрой это тестом на трёх примерах из раздела 2 спецификации. В подробностях события покажи и `receivedAtUtc`; при большой разнице (больше 5 минут) — пометку «доставлено позже».
- Для стабильных относительных времён в mock используй инжектируемый `TimeProvider`: данные строятся один раз относительно момента старта и не перегенерируются при обновлении.

## A.7. Архитектура проектов и тесты

Тестовый проект на `net10.0` не может сослаться на MAUI-проект с `net10.0-android` и т. п. Поэтому:

- Создай библиотеку **`TelemetryMobile.Core`** (`net10.0`, без зависимостей от MAUI): модели, интерфейс источника данных, `MockDeviceTelemetryService`, `ApiDeviceTelemetryService` с DTO, каталог кодов, сессия, форматирование относительного времени, ресурсы локализации (`.resx`) и — по возможности — ViewModel (CommunityToolkit.Mvvm не зависит от MAUI). MAUI-зависимости (`Preferences`, Shell-навигация, `MainThread`) спрячь за маленькими интерфейсами (`ISettingsStore`, `INavigationService` и т. п.), реализованными в MAUI-проекте.
- Создай **`TelemetryMobile.Tests`** (xUnit, `net10.0`), ссылающийся только на Core. Добавь оба проекта в `TelemetryMobile.slnx`. Тесты должны запускаться без MAUI workloads: `dotnet test TelemetryMobile.Tests`.
- К тестам из раздела 13 части B добавь:
  - разбор JSON-примеров из спецификации (карточка, страница событий, `payload: null`, даты с 0/5/7 знаками дробной части);
  - маппинг Problem Details → типизированная ошибка (404 `device.not_found`, 404 `customer.not_found`, 400 `pagination.invalid_cursor`, 429 с `Retry-After`, 400 с `errors` без `code`) через фейковый `HttpMessageHandler`;
  - формирование URL: `limit`, URL-кодирование `cursor`, отсутствие `cursor` на первой странице;
  - пагинацию mock: страницы не пересекаются и не теряют события с одинаковым временем, `hasMore`/`nextCursor` корректны на последней странице;
  - что каждый ключ английского `.resx` есть и не пуст в `de` и `ru`;
  - русские формы множественного числа в относительном времени (1 минуту / 2 минуты / 5 минут / 21 минуту).

## A.8. Локализация — технические решения

- `.resx` (en по умолчанию, `de`, `ru`) в Core + синглтон-менеджер локализации с индексатором `this[string key]`, который при смене языка выставляет `CultureInfo.CurrentUICulture`/`CurrentCulture` (и `DefaultThread…`) и поднимает `PropertyChanged("Item[]")`. В XAML — привязка к индексатору через `Source` с явным `x:DataType` (compiled bindings).
- Строки, вычисляемые во ViewModel (статусы, относительное время, даты, счётчики), пересчитываются по событию смены языка — проверь это на каждом открытом экране, включая страницы в стеке навигации.
- Язык по умолчанию — язык устройства, если это en/de/ru, иначе en. Выбор сохраняется в `Preferences`.
- Строки из enum и кодов — только через presentation-слой (конвертер или форматтер), не в моделях.

## A.9. Навигация

Shell не поддерживает пути вида `/devices/{deviceId}` — используй Shell-маршруты с query-параметром `deviceId`, например `//devices`, `device?deviceId=15`, `device/events?deviceId=15` (точные имена на твоё усмотрение). Login и Devices — корневые `ShellContent`; переход Login → Devices и Logout → Login делай абсолютными маршрутами (`//…`), чтобы стек очищался. При запуске с сохранённой сессией открывай Devices сразу; Logout очищает сессию и кэш данных.

# Часть B. Исходное техническое задание

## 1. Роль и цель

Ты выступаешь в роли Senior .NET MAUI Engineer, UI/UX Designer и Mobile Application Architect.

В существующем репозитории уже создан проект .NET MAUI с демонстрационным контентом. Не создавай новое приложение с нуля. Изучи существующий проект и преврати его в аккуратное, современное и функциональное MVP для мониторинга устройств и просмотра телеметрии.

## 3. Концепция продукта и визуальный стиль

Приложение предназначено для мониторинга IoT-устройств, их состояния, health-check и истории событий.

Визуально это должен быть современный инструментальный интерфейс, напоминающий качественные приложения для мониторинга инфраструктуры и IoT.

### Предлагаемая концепция

Название приложения: `DeviceTelemetry`.

Основная стилистика:

- Современный минимализм.
- Аккуратные карточки с умеренным скруглением.
- Чёткая визуальная иерархия.
- Достаточно свободного пространства.
- Тонкие разделители и неброские границы.
- Контрастная типографика.
- Минимум декоративных элементов.
- Плавные, ненавязчивые анимации там, где они действительно полезны.
- Отсутствие визуального шума и чрезмерного количества градиентов.

Предпочтительная палитра:

- Основной фон: очень светлый холодный серо-голубой или тёмный navy — выбери один основной вариант и выдержи его последовательно.
- Карточки: белые или слегка приподнятые поверхности.
- Основной текст: тёмно-синий графит.
- Вторичный текст: спокойный серо-голубой.
- Акцент: насыщенный синий или индиго.
- Успешное состояние: мягкий зелёный с хорошо читаемым текстом.
- Ошибка: приглушённый красный.
- Предупреждение: янтарный.

Не используй яркие красные и зелёные заливки на больших участках экрана. Индикаторы должны быть заметными, но не агрессивными.

Предусмотри централизованные ресурсы темы:

- отступы;
- радиусы;
- размеры иконок;
- стили карточек;
- стили кнопок;

Если проект уже поддерживает светлую и тёмную темы, сохрани эту возможность. Если нет, реализуй один качественный вариант оформления, не превращая поддержку двух тем в отдельный большой проект.

### UX-требования

- Основные действия доступны большим удобным элементам управления.
- Интерфейс хорошо читается на небольших экранах.
- Текст не обрезается при немецкой локализации.
- Длинные названия устройств не ломают карточки.
- Состояния loading, empty и error предусмотрены заранее.
- Все интерактивные элементы имеют визуальную обратную связь.
- Не используй emoji в качестве основных иконок интерфейса. Предпочтительны векторные иконки или существующий набор ресурсов проекта.
- Учитывай safe areas, системную клавиатуру и прокрутку.

## 4. Экран входа — Login

При первом запуске пользователь должен видеть экран входа.

### Состав экрана

- Название или логотип приложения DeviceTelemetry.
- Короткий подзаголовок, например `Monitor your connected devices`.
- Поле `Customer ID`.
- Поле `Password`.
- Кнопка `Login`.
- Переключатель языка EN / DE / RU.

Можно добавить небольшую ненавязчивую графическую деталь, связанную с мониторингом устройств, если она улучшает композицию.

Не перегружай экран иллюстрациями и декоративными элементами.

### Поведение

`Customer ID` — обязательное поле.

`Password` — обязательное поле для демонстрации, но значение никуда не отправляется и не проверяется сервером.

При нажатии `Login`:

1. Проверить, что `Customer ID` заполнен.
2. Выполнить минимальную клиентскую валидацию.
3. Сохранить введённый `Customer ID` в локальном состоянии приложения.
4. Перейти на главный экран со списком устройств.

Никакие HTTP-запросы при логине не выполняются.

Не создавай фиктивный backend и не имитируй сетевую авторизацию.

Пароль не сохраняй в Preferences, SecureStorage, обычных файлах или других хранилищах. После успешного перехода очисти пароль из состояния формы, насколько это позволяет выбранная реализация.

Для локального хранения `CustomerId` используй существующий механизм приложения или небольшой интерфейс, например `ICurrentSession`. Если нужно сохранять его между запусками, используй `Preferences`.

Не храни пароль.

### UX входа

- Поле Customer ID должно поддерживать понятную клавиатуру.
- Ошибки валидации должны отображаться непосредственно рядом с полями.
- При пустом Customer ID нельзя переходить на главный экран.
- Enter/Return на клавиатуре по возможности должен активировать логин.
- После успешного входа пароль должен исчезать из формы.
- Все тексты должны локализоваться.

Для демонстрационного MVP не нужна регистрация, восстановление пароля или реальная аутентификация.

## 5. Главный экран — Devices

После входа открывается главный экран пользователя.

Предлагаемый маршрут:

`/devices`

### Верхняя часть

Отобрази:

- Приветствие, например `Welcome back`.
- Имя или идентификатор текущего клиента.
- Заголовок `My devices`.
- Общее количество устройств.
- Небольшую сводку: количество устройств с нормальным состоянием и количество требующих внимания.

Не выдумывай реальные значения из API: до его подключения используй явно демонстрационные данные.

Предусмотри кнопку или иконку перехода к настройкам, включая выбор языка и выход из демонстрационной сессии.

### Список устройств

Устройство отображается в виде современной карточки.

Предлагаемый состав карточки:

- Имя устройства.
- Компактный идентификатор или код устройства.
- Индикатор состояния: Online, Warning, Offline или Unknown.
- Время последнего события.
- Время последнего health-check.
- Последний известный код статуса, если есть.
- Иконка перехода к подробностям.

Пример визуальной композиции:

    ┌────────────────────────────────┐
    │ ●  Temperature Sensor          │
    │    DEVICE-001                  │
    │                                │
    │    Online                      │
    │    Last event   2 min ago      │
    │    Health check 30 sec ago     │
    │                            ›   │
    └────────────────────────────────┘

Это только концепция. Реализуй визуально более качественный вариант, соответствующий общей дизайн-системе.

Карточка должна иметь понятные состояния:

- `Online` — зелёный индикатор.
- `Warning` — янтарный.
- `Offline` — красный или нейтрально-красный.
- `Unknown` — серый.

Цвет не должен быть единственным способом различить состояние. Всегда показывай текстовый статус.

### Правила определения статуса

Не делай вид, что backend уже умеет определять Online/Offline.

Существующая модель может не содержать формального heartbeat-протокола и порогов актуальности health-check.

Поэтому:

- Подготовь модель состояния, которую можно будет получать из API.
- Для демонстрационных данных используй заранее определённые состояния.
- Не вычисляй статус из произвольного `StatusCode`, если отсутствует соответствующая бизнес-логика.
- Если время последнего health-check неизвестно, показывай локализованный текст вроде `No health check`.
- Не подменяй отсутствие информации состоянием Online.

### Дополнительные элементы

Можно добавить строку поиска устройств, если она естественно вписывается в дизайн.

Поиск должен реально фильтровать локальный список по имени или DeviceCode.

Не добавляй сложную фильтрацию и сортировку без необходимости.

### Empty state

Если у клиента нет устройств, покажи аккуратное пустое состояние:

- иконка устройства;
- текст `No devices yet`;
- пояснение;
- действие обновления списка, если оно предусмотрено интерфейсом источника данных.

Не показывай пустой экран или бесконечный индикатор загрузки.

### Верхняя часть

Не показывай фальшивые графики, которые выглядят как реальные измерения.

Если значение отсутствует, показывай локализованный placeholder, например `Not available`.

Не добавляй нефункциональные кнопки, создающие впечатление, что уже реализованы управление устройством или удалённая настройка.

## 7. Экран событий — Device Events

### Состав экрана

- Заголовок `Event history`.
- Список событий в обратном хронологическом порядке.
- Дата и время события.
- Код статуса.
- Краткое описание, если оно доступно.
- Индикация типа события, если его можно определить из данных.

Каждое событие должно иметь аккуратный визуальный маркер.

Если Payload содержит структурированные данные, подготовь возможность показать их в подробностях события. Не выводи произвольный JSON целиком в карточке списка.

В демонстрационных данных должны присутствовать разные типы событий:

- нормальный health-check;
- предупреждение;
- ошибка;
- восстановление после ошибки.

Не делай вывод о типе события только по числовому коду без определённого правила.

Если описание неизвестно, отображай нейтральное локализованное сообщение вроде `Status update`.

Реализуй полноценную локализацию трёх языков:

- Deutsch (`de`);
- Русский (`ru`).

- кнопки;
- заголовки;
- поля ввода;
- placeholder-ы;
- сообщения об ошибках;

- диалоги;

Не ограничивайся локализацией только стартового экрана.

### Выбор технологии

Сначала проверь текущую инфраструктуру локализации проекта.

Если её нет, выбери подходящий для MAUI механизм. Предпочтительно использовать стандартные `.resx`-ресурсы с `ResourceManager` и корректно настроенным обновлением привязанных строк либо уже используемую библиотеку локализации, если она подходит.

Названия и расположение файлов адаптируй к требованиям текущего проекта.

Пользователь должен иметь возможность сменить язык:

- на экране входа;
- после входа — в настройках или меню приложения.

Выбранный язык сохраняется в `Preferences` и восстанавливается при следующем запуске.

При смене языка UI должен обновляться сразу, без обязательного перезапуска приложения.

Проверь, что изменение языка обновляет все активные страницы, включая заголовки, статусы, пустые состояния и форматирование дат.

Не смешивай локализованные отображаемые строки с бизнес-логикой.

В модели состояния храни стабильные значения или enum, а преобразование в текст выполняй через локализуемый presentation layer.

Используй корректное форматирование с учётом культуры.

В UI показывай локальное время устройства пользователя, если нет иных требований.

Относительные даты вроде `2 minutes ago` должны корректно локализоваться на всех трёх языках.

Не хардкодь английские суффиксы времени в ViewModel.

## 9. Архитектура приложения

Подготовь приложение к дальнейшему подключению реального REST API.

Предпочтительная архитектура:

- Views — XAML-страницы.
- ViewModels — состояние экрана и команды.
- Models / DTOs — модели представления и контракты.
- Services — бизнес-сценарии, навигация, локальная сессия, локализация.
- Data — mock-источник данных.

Не нужно механически создавать каждый каталог, если структура проекта уже организована иначе.

### ViewModels

Реализуй отдельные ViewModel для:

- Login.
- Devices.
- Device Details.
- Device Events.
- Settings, если настройки выделяются в отдельный экран.

Используй `CommunityToolkit.Mvvm`, если он уже подключён или его добавление оправдано.

Не размещай бизнес-логику в code-behind. Code-behind допустим для чисто визуального поведения, которое не имеет смысла переносить в ViewModel.

### Источник данных

Создай абстракцию для получения устройств и событий, например `IDeviceTelemetryService`.

Она должна позволять заменить mock-реализацию на HTTP-клиент без изменения ViewModel и XAML.

Пример направления:

```csharp
public interface IDeviceTelemetryService
{
    Task<IReadOnlyList<DeviceDto>> GetDevicesAsync(
        int customerId,
        CancellationToken cancellationToken);

    Task<DeviceDetailsDto?> GetDeviceDetailsAsync(
        int deviceId,
        CancellationToken cancellationToken);

    Task<IReadOnlyList<DeviceEventDto>> GetDeviceEventsAsync(
        int deviceId,
        CancellationToken cancellationToken);
}
```

Это пример, а не обязательный контракт. Адаптируй его к моделям и спецификации API, которую я предоставлю отдельно.

Реализуй `MockDeviceTelemetryService`, который возвращает демонстрационные данные.

Mock-данные должны быть согласованными: события принадлежат соответствующим устройствам, а устройства относятся к выбранному CustomerId.

Не создавай случайные значения при каждом обновлении экрана, если это делает интерфейс нестабильным.

Все зависимости регистрируй через DI в `MauiProgram.cs`.

### Навигация

Используй существующую систему навигации.

Если проект использует Shell, не добавляй вторую систему навигации.

Навигация должна поддерживать:

- Login → Devices.
- Devices → Device Details.
- Device Details → Device Events.
- Возврат на предыдущий экран.
- Logout → Login.

После выхода из приложения или демонстрационной сессии не оставляй пользователя на экране устройств с предыдущим CustomerId.

### Состояния экранов

Для асинхронных операций предусмотри:

- `IsBusy`;
- состояние загрузки;
- состояние ошибки;
- состояние отсутствия данных.

Сейчас mock-источник может работать быстро, но ViewModel должна быть готова к сетевым задержкам в будущем.

Не добавляй искусственные задержки ради имитации сети без необходимости.

## 10. Подготовка к API

Спецификация REST API будет предоставлена отдельно.

До её изучения не придумывай реальные HTTP-контракты и не реализуй сетевые вызовы.

На текущем этапе:

- данные устройств поступают из mock-источника;
- события поступают из mock-источника;
- логин ничего не отправляет;
- CustomerId используется для выбора локальных демонстрационных данных;
- интерфейс источника данных должен быть совместим с будущей реализацией API.

Когда спецификация станет доступна, не изменяй внешний вид и ViewModel без необходимости. Реализуй новый источник данных, который использует реальные DTO и endpoint-ы.

Не используй `HttpClient` внутри страниц или ViewModel.

Не сохраняй в `Preferences` фиктивные токены или пароль.

## 11. Демонстрационные данные

Создай достаточно данных, чтобы интерфейс выглядел реалистично.

Рекомендуемый набор:

- 5–8 устройств;

- одно устройство Warning;
- одно устройство Offline;

- разные времена последних событий и health-check;
- несколько событий для каждого устройства;
- события с разными статусами и Payload.

Используй понятные названия устройств, например:

- Water Meter.
- Power Monitor.

Это только демонстрационные названия.

- для другого CustomerId устройств нет.

Для остальных CustomerId можно возвращать пустой список либо использовать один явно документированный fallback-сценарий.

- стабильное отображение списка после перехода на карточку и возврата.

Не добавляй сложную анимационную систему, графики или сторонние UI-библиотеки без конкретной пользы.

Приоритет — стабильный интерфейс, хороший визуальный результат и понятная структура кода.

## 13. Тестирование

Используй существующую тестовую инфраструктуру, если она есть.

Добавь тесты как минимум для:

- проверки обязательного CustomerId при входе;
- успешного входа и сохранения CustomerId;
- отсутствия сохранения пароля;
- получения устройств для правильного клиента;
- пустого списка для клиента без устройств;
- получения событий выбранного устройства;
- локальной фильтрации списка, если реализован поиск;
- корректного завершения демонстрационной сессии.

Если тестировать MAUI ViewModel непосредственно затруднительно, выдели необходимую бизнес-логику в обычные .NET-классы, не зависящие от UI.

Не добавляй сложную тестовую инфраструктуру ради нескольких простых тестов.
